# 実行委員は開催年の中身だけを扱い、開催年・カテゴリ・ステージと過去の開催のデータは変えさせない

中身は年ごとに持つ（ADR 0003）。開催年の中身は、運営が入れて公開する。前の年までの中身は、次の年に入力するときの参考として残し、変えない。

管理画面は運営の道具で、管理者（EmDash の Admin）と実行委員（Editor）が使う。出展者・出演者・協賛は管理画面を使わず、編集用の鍵の専用フォームで自分の一件だけを書き換える（ADR 0001）。

| | 管理者 | 実行委員 |
|---|---|---|
| 開催年を決める | できる | できない |
| 開催年のカテゴリ・ステージを作る・直す・公開する・消す | できる | できない |
| 開催年のほかの中身を作る・直す・公開する・消す | できる | できる |
| 過去の開催のデータを直す・公開する・公開を取り消す | できる（間違いを直すときだけ） | できない |
| 過去の開催のデータを消す・ゴミ箱から戻す | できる | できない |
| 中身を複製する（過去の開催のデータを、開催年の下書きの元にするなど） | できる（複製の後に年を開催年に直す） | できない |
| 過去の開催のデータを古い版に戻す・公開を予約する | できる | できない |
| MCP で操作する | できる | できない |

- 開催年: 自作プラグイン（`cms/src/plugins/admin-guard.ts`）の設定に置く。変えられるのは Admin だけで、「開催年」のページは Admin でない人の変更を断り、MCP の道具の経路は `plugins:manage` を求める（ADR 0009）。
- 実行委員の保存・公開・公開の取り消し・公開の予約: プラグインのフック（`content:beforeSave`・`content:beforePublish`・`content:beforeUnpublish`・`content:beforeSchedule`）で、カテゴリ・ステージと、過去の開催のデータを断る。年が開催年でない保存も断る。
- 複製: 保存のフックを通らず、前の年の年がそのまま写る。`middleware.ts` で実行委員の複製を断る。
- 削除・完全な削除・ゴミ箱からの復元: `middleware.ts` で、実行委員が過去の開催のデータに対して行う要求を断る。削除のフック（`content:beforeDelete`）には操作した人が渡らず、復元にはフックが無いため、プラグインでは管理者と実行委員を分けられない。カテゴリとステージの要求は、GET 以外をすべて `middleware.ts` で実行委員から断る。
- 版の復元: 保存のフックを通らない。`middleware.ts` で、実行委員が過去の開催のデータに行う復元と、前の年の版を戻す復元を断る。
- MCP: 同じ Worker の `/_emdash/api/mcp` で動き、`middleware.ts` を通る。実行委員の MCP は一律に断る。管理者の MCP の保存・公開には操作した人が渡るので、フックは管理者として扱う。
- 参照の候補: カテゴリとステージを選ぶ候補は、開催年のものだけにする。`middleware.ts` で、候補の要求に年の絞り込み（`fieldFilters`）を足す。

EmDash の役割は、ブログのように「誰が書き、誰が確かめて公開するか」を決めるためのもので、どの種類の操作ができるかを全部の中身に一律で決める。Editor はどのコレクションでも作る・直す・消すができ、分類も管理できる。コレクションごと・年ごとに分ける設定は無い（1.3.0・1.4.0）。そのため、ここで決めたことは自分たちで守る。

## Considered Options

- カテゴリとステージを EmDash の分類（taxonomy）にして、サイドバーの「管理」に出す: 分類の項目には年を持たせられない。項目の作成と削除は保存のフックを通らず、Editor（`taxonomies:manage`）が編集画面から作れる。公開中の中身の分類を変えると、公開を待たずに効く（emdash-cms/emdash#4032 が未 merge）。守る仕組みを middleware だけで作ることになり、壊れやすいので採らなかった。
- 過去の開催のデータを管理者にも直させない: 公開した後に見つかった誤り（名前の誤字など）を直せなくなるので採らなかった。
- 過去の開催のデータを管理者にも消させない（`content:beforeDelete` で一律に断る）: どうしても消したいとき（個人の情報を載せてしまったなど）に、年を開催年に書き換えてから消すという回り道が要るので採らなかった。
- 開催年を `.env` や Worker の変数に置く: 変えるのにデプロイが要り、管理画面から決められないので採らなかった。
- 年の項目の既定値（コンテンツの種類の設定）だけで済ませる: 既定値は新しく作るときの初期値で、実行委員が書き換えられるので採らなかった。
- 実行委員が違う年で保存したら、黙って開催年に直す: 保存した後に年が変わり、入れた人が気づけないので採らなかった。
- 実行委員の複製を許し、複製の後に年を開催年に直す: 複製は保存のフックを通らないので、年を直すには EmDash の内部の処理を middleware から呼ぶことになる。写った前の年の下書きは、実行委員には直せず消せもしないので採らなかった。
- 実行委員にも MCP を使わせ、要求の中身（呼ぶ道具の名前）を読んで削除・復元・複製・版の復元だけを断る: 複数の要求をまとめる形や slug での指定まで追うことになり、EmDash を上げたときに壊れやすいので採らなかった。実行委員は画面だけを使う。
- 出展者・出演者の候補も開催年に絞る: 同じ候補の要求を「前回の出展」（前の年を選ぶ）も使い、見分けられないので採らなかった。

## Consequences

- 実行委員にも、カテゴリ・ステージ・過去の開催のデータの画面と編集のボタンは出る。保存や削除をしたときに断られる。サイドバーから項目を消す仕組みは無い。
- `middleware.ts` は、管理画面が呼ぶ API の形（パスと、候補の要求に `page` が無いこと、一覧の API が `context.url` を読むこと、削除する中身の年を `locals.emdash.handleContentGetIncludingTrashed` で読めること）に頼る。EmDash を上げたときは、`docs/notes/admin-guard-checks.md` の確かめ方を流す。
- 実行委員は MCP を使えない。AI の agent に中身を入れさせるときは、管理者の token を使う。
- 年が変わるときは、管理者が開催年を変え、その年のカテゴリとステージを作る。それまでの年の中身は、その時点から実行委員には変えられなくなる。開催年から決まるもの（年の既定値・一覧・候補）は ADR 0009。
- 実行委員は、中身以外の EmDash の機能（分類・メニュー・ウィジェット・セクション・署名）を変えられる。公開サイトはこれらを読まないので、公開サイトには出ない。
